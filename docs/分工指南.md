# TPC CommerceInsight 数据库课程设计最新四人分工指南 V3

> 项目名称：**TPC CommerceInsight**  
> 完整名称：**TPC CommerceInsight: E-commerce Data Management and Benchmark Analysis System**  
> 技术路线：**SpringBoot + Vue 3 + Element Plus + ECharts + PostgreSQL Docker + MyBatis/JDBC + Python 多线程性能测试脚本**  
> 数据库部署：**Docker 部署 PostgreSQL，不使用 openGauss**  
> 分工原则：**契约先行、SQL 源目录唯一、命名规范冻结、Mock 统一、联调分层、D 不成为新瓶颈。**

---

## 0. 本版修订重点

本版在上一版基础上补充并修正 5 个容易导致后期联调混乱的问题：

1. **明确 `sql/` 与 `db/init/` 的关系**：`sql/` 是数据库 SQL 资产源目录，`db/init/` 只是 Docker 初始化入口，不单独维护业务 SQL。
2. **冻结 PostgreSQL 命名规范**：所有表名、字段名、索引名、约束名均使用小写加下划线，不使用双引号创建对象。
3. **明确 D 的边界，避免“协助”变成混责**：D 负责正式环境、正式数据、性能测试执行和报告总控；A/B/C 只向 D 提交各自领域的明确交付物，不把 Docker、压测、报告整合责任转移给 A/B/C，也不让 D 替 A/B/C 修代码、写章节。
4. **区分系统演示导入与正式数据初始化导入**：B/C 做页面和接口导入，D 做 Docker 环境下的 TPC-H 正式数据装载。
5. **统一 Mock 契约**：`docs/api/mock-contract.md` 是 B 的 Mock Repository 和 C 的 Mock JSON 的唯一字段来源。
6. **冻结跨层字段边界**：C 只依赖 API JSON 字段，不依赖数据库字段；A 不因为前端字段名偏好直接修改数据库字段，字段转换由 B 的 DTO/VO 完成。

## 1. 项目目标

本项目面向数据库课程设计，要求实现一个基于 TPC-H / TPC-C Benchmark 的电商数据管理与性能分析系统。系统不仅要完成基本的数据管理与业务查询，还要体现数据库系统课程的核心能力：

1. 大规模 TPC-H 数据生成与导入；
2. 数据批量导入、字段清洗与错误日志记录；
3. 用户管理与权限控制；
4. TPC-H 复杂查询与统计分析；
5. TPC-C 事务处理；
6. 存储过程与触发器；
7. 索引设计与执行计划分析；
8. TPC-H / TPC-C 并发测试；
9. 查询结果与性能指标图形化展示；
10. 完整课程设计报告与验收演示。

最终目标不是简单做一个 Web 系统，而是做一个具有数据库设计、事务处理、查询优化和性能测试证据链的高分课程设计项目。

### 3.2 `sql/` 与 `db/init/` 的关系

必须明确以下规则，避免 SQL 资产分裂：

| 目录 | 负责人 | 作用 | 是否允许写业务 SQL |
|---|---|---|---|
| `sql/` | A | 数据库 SQL 资产源目录，保存表结构、约束、触发器、存储过程、索引、查询 SQL | **允许，且只能在这里维护正式 SQL 逻辑** |
| `db/init/` | D | Docker 初始化执行目录，用于 PostgreSQL 容器首次启动时执行初始化 | **不允许单独维护业务 SQL，只允许引用 `sql/`** |

### 3.3 正式执行入口

Docker 初始化的正式入口是：

```text
db/init/00_run_sql_assets.sh
```

该脚本只负责按顺序执行 A 提供的 `sql/V*.sql`，不直接写表结构、字段、约束、触发器、存储过程等业务 SQL。

推荐 `docker-compose.yml` 中同时挂载 `sql/` 和 `db/init/`：

```yaml
services:
  postgres:
    image: postgres:16
    container_name: tpc-commerce-postgres
    environment:
      POSTGRES_USER: tpc_admin
      POSTGRES_PASSWORD: tpc_password
      POSTGRES_DB: tpc_commerce
    ports:
      - "5432:5432"
    volumes:
      - postgres_data:/var/lib/postgresql/data
      - ../sql:/sql:ro
      - ./init:/docker-entrypoint-initdb.d:ro

volumes:
  postgres_data:
```

推荐 `db/init/00_run_sql_assets.sh`：

```bash
#!/usr/bin/env bash
set -euo pipefail

psql -v ON_ERROR_STOP=1 --username "$POSTGRES_USER" --dbname "$POSTGRES_DB" <<'SQL'
\i /sql/V1__create_tpch_tables.sql
\i /sql/V2__create_tpcc_tables.sql
\i /sql/V3__create_app_tables.sql
\i /sql/V4__add_constraints.sql
\i /sql/V8__triggers.sql
\i /sql/V9__procedures.sql
\i /sql/V10__indexes_baseline.sql
SQL
```

说明：

1. `V5__tpch_queries.sql`、`V6__tpcc_transaction_sql.sql`、`V12__explain_baseline.sql` 通常是查询和测试脚本，不一定需要容器初始化时自动执行。
2. `V11__sample_data.sql` 可用于 A 的本地自测或 D 的 SF=0.1 前置验证，正式 SF=1 数据应由 D 使用 COPY 脚本导入。
3. 如果需要把某个脚本纳入 Docker 初始化，必须先由 A 提交到 `sql/`，再由 D 调整 `00_run_sql_assets.sh` 的引用顺序。
4. `00_run_sql_assets.sh` 必须使用 LF 换行，避免 Linux 容器中出现 `/usr/bin/env: bash\r` 错误。
5. `00_run_sql_assets.sh` 必须有可执行权限；在 Windows 上提交前由 D 在 Git Bash/WSL 中执行 `chmod +x db/init/00_run_sql_assets.sh`，并用 `git ls-files --stage db/init/00_run_sql_assets.sh` 确认文件模式为 `100755`。

### 3.3.1 开发初始化模式与正式导入模式

开发初始化和正式导入的 SQL 执行顺序不同，不能混用。

| 模式 | 目的 | 执行顺序 | 是否导入大规模 TPC-H 数据 |
|---|---|---|---|
| 开发初始化模式 | A/B/C 本地快速启动、样例数据联调 | `V1` 建 TPC-H 表 -> `V2` 建 TPC-C 表 -> `V3` 建应用表 -> `V4` 约束 -> `V8` 触发器 -> `V9` 存储过程 -> `V10` 索引 -> 可选 `V11` 样例数据 | 否，只使用样例数据 |
| 正式导入模式 | D 构建验收和性能测试数据库 | `V1` 建 TPC-H 表 -> `V2` 建 TPC-C 表 -> `V3` 建应用表 -> 先 COPY 导入 TPC-H 数据 -> `V4` 约束 -> `V8` 触发器 -> `V9` 存储过程 -> `V10` 索引 -> 行数统计和 EXPLAIN | 是，使用 SF=0.1/SF=0.6/SF=1 |

正式导入模式中，大表数据建议在外键和部分索引之前导入，以减少 COPY 失败定位成本和初始化耗时；开发初始化模式优先保证脚本简单、顺序稳定、可重复。

### 3.4 SQL 变更同步规则

任何数据库结构或逻辑变更必须遵守：

```text
先改 sql/ 源脚本
再由 D 更新 db/init/ 的引用顺序或执行脚本
最后重建/重置 Docker 数据库验证
```

禁止：

```text
A 改 sql/V1__create_tpch_tables.sql
D 又在 db/init/01_create_tpch_tables.sql 手写另一份表结构
B 连接数据库后字段对不上
```

### 3.5 SQL 变更记录

每次数据库契约变更，都要在 `docs/database/table-contract.md` 或 `docs/database/change-log.md` 中记录：

```text
变更日期
变更人
变更脚本
变更对象
是否影响 B 的实体类/Mapper
是否影响 C 的 Mock JSON
是否影响 D 的 Docker 初始化或导入脚本
```

## 4. 数据库命名规范

### 4.1 总原则

PostgreSQL 中所有数据库对象统一使用：

```text
小写字母 + 下划线 snake_case
```

禁止使用双引号创建表名和字段名。

### 4.2 表名规范

所有表名使用小写：

```text
region
nation
supplier
part
partsupp
customer
orders
lineitem
warehouse
district
tpcc_customer
tpcc_orders
new_order
order_line
item
stock
app_user
import_task
import_error_log
query_log
transaction_log
performance_result
```

说明：

1. TPC-H 的 `customer`、`orders`、`lineitem` 等表使用标准语义，但表名全部小写。
2. TPC-C 中也存在 `customer`、`orders` 等概念，为避免与 TPC-H 冲突，TPC-C 客户和订单表建议使用 `tpcc_customer`、`tpcc_orders`。
3. PostgreSQL 中 `order` 是关键字，不要使用 `order` 作为表名。

### 4.3 字段名规范

字段名全部小写，保留 TPC-H/TPC-C 原始语义和前缀。

TPC-H 示例：

```text
region.r_regionkey
nation.n_nationkey
supplier.s_suppkey
part.p_partkey
partsupp.ps_partkey
partsupp.ps_suppkey
customer.c_custkey
orders.o_orderkey
orders.o_custkey
lineitem.l_orderkey
lineitem.l_linenumber
```

不允许：

```sql
CREATE TABLE "ORDERS" (
  "O_ORDERKEY" integer
);
```

推荐：

```sql
CREATE TABLE orders (
  o_orderkey integer NOT NULL,
  o_custkey integer NOT NULL,
  o_orderstatus char(1) NOT NULL,
  o_totalprice numeric(15, 2) NOT NULL,
  o_orderdate date NOT NULL,
  o_orderpriority char(15) NOT NULL,
  o_clerk char(15) NOT NULL,
  o_shippriority integer NOT NULL,
  o_comment varchar(79) NOT NULL
);
```

### 4.4 约束、索引、触发器命名规范

```text
主键：pk_<table>
外键：fk_<from_table>_<to_table>
唯一约束：uk_<table>_<columns>
检查约束：ck_<table>_<condition>
索引：idx_<table>_<columns>
触发器：trg_<table>_<action>
函数：fn_<business_name>
存储过程：sp_<business_name>
```

示例：

```sql
ALTER TABLE orders
  ADD CONSTRAINT pk_orders PRIMARY KEY (o_orderkey);

ALTER TABLE lineitem
  ADD CONSTRAINT fk_lineitem_orders
  FOREIGN KEY (l_orderkey) REFERENCES orders(o_orderkey);

CREATE INDEX idx_lineitem_shipdate ON lineitem(l_shipdate);
```

### 4.5 数据库字段与 API 字段映射

数据库层统一使用 `snake_case`，API JSON 层统一使用 `lowerCamelCase`。

示例：

| 数据库字段/SQL 别名 | API JSON 字段 |
|---|---|
| `nation_name` | `nationName` |
| `total_revenue` | `totalRevenue` |
| `elapsed_ms` | `elapsedMs` |
| `row_count` | `rowCount` |

B 负责在 DTO 或 VO 中完成映射，C 只依赖 API JSON 字段，不直接依赖数据库字段大小写或 SQL 别名。A 不因为前端字段名偏好直接修改数据库字段；如果 C 需要 `lowerCamelCase` 字段，由 B 在接口层转换。

## 6. 数据导入职责边界

### 6.1 两类导入必须区分

| 类型 | 目的 | 负责人 | 使用场景 | 技术方式 |
|---|---|---|---|---|
| 系统演示导入 | 展示课程要求中的数据批量导入、清洗、错误日志、进度条 | B/C 主责，A 提供规则，D 提供测试文件 | 验收演示页面 | 用户通过页面上传或指定文件，后端分批读取、清洗、批量写入 |
| 正式数据库初始化导入 | 构建完整 TPC-H 数据库，用于统计分析、性能测试、报告数据 | D 主责，A 提供表结构和 COPY 兼容要求 | Docker 环境初始化、正式测试 | dbgen 生成数据，D 用 COPY 或脚本导入完整数据 |

### 6.2 系统演示导入

系统演示导入要求：

```text
1. 至少支持 2 张大表，例如 orders + lineitem，或 orders + partsupp。
2. 支持页面选择表名和文件。
3. 支持分批读取，不一次性读入完整文件。
4. 按 A 的清洗规则进行类型、范围、空值、日期检查。
5. 错误数据写入 import_error_log 或日志文件。
6. 合法数据继续导入。
7. 页面展示进度、成功条数、失败条数、耗时。
```

责任划分：

| 成员 | 职责 |
|---|---|
| A | 定义每张表的清洗规则、字段类型、主键冲突策略、导入 SQL 模板 |
| B | 实现导入任务接口、分批读取、程序侧校验、批量写入、错误日志接口 |
| C | 实现导入页面、进度条、错误日志展示、导入结果截图 |
| D | 提供带错误行的测试文件，协助验证导入结果 |

### 6.3 正式数据库初始化导入

正式数据库初始化导入要求：

```text
1. 使用 dbgen 生成 SF=0.1 开发数据和 SF=0.6/SF=1 正式数据。
2. 使用 PostgreSQL COPY 或脚本导入完整 TPC-H 数据。
```

## 16. 风险控制清单

| 风险 | 解决办法 |
|---|---|
| A 改了 `sql/`，D 的 Docker 初始化还是旧 SQL | `db/init/` 不维护业务 SQL，只引用 `sql/`，变更必须先改 `sql/` |
| PostgreSQL 大写字段导致 SQL 需要双引号 | 全部使用小写 snake_case，不使用双引号 |
| D 任务过重成为新瓶颈 | 明确 D 只负责正式环境、正式实验执行和整合；A 提交 SQL/索引/EXPLAIN 解读材料，B 提交稳定可测接口，C 提交性能图表与截图，D 不代写、不代修、不代做 |
| B 的导入接口和 D 的正式导入混淆 | B/C 做系统演示导入，D 做正式数据库初始化导入 |
| B/C Mock 字段不一致 | `docs/api/mock-contract.md` 是唯一字段来源 |
| C 依赖数据库字段导致前端随 SQL 变更崩溃 | C 只依赖 API JSON 字段；数据库字段和 SQL 别名由 B 在 DTO/VO 层映射 |
| A 被前端字段名牵着改数据库字段 | 数据库字段按 TPC-H/TPC-C 和命名规范冻结；前端字段名变化只改 API 契约和 B 的映射 |
| 开发初始化与正式导入执行顺序混用 | 在文档和脚本中明确区分两种模式，开发模式可执行样例数据，正式模式先 COPY 大表再加约束/索引 |
| `00_run_sql_assets.sh` 在容器内无法执行 | 文件必须使用 LF 换行，并提交 `chmod +x` 后的可执行权限 |
| C 等 B 接口导致前端停工 | C 先用统一 Mock JSON 开发 |
| B 等 A 数据库导致后端停工 | B 先用 Mock Repository 开发 |
| 正式 SF=1 数据导入太慢 | 先保证 SF=0.1 可演示，SF=1 用于最终性能测试，必要时使用 SF=0.6 保底 |
| TPC-C 完整实现过难 | 只做 New-Order 和 Payment 两个可演示事务 |
| 报告最后一天补不完 | 第 1 天建报告目录，第 3 天开始放截图，第 6 天只做整合 |

## 17. 最终结论

本版分工的核心是：

```text
A 管 SQL 源资产，保证数据库设计扎实；
B 管后端接口和事务，保证业务服务可用；
C 管前端、Mock 和前后端联调，保证系统可演示；
D 管 Docker、正式数据、性能实验和报告总控，保证项目可交付。
```

最关键的工程规则是：

```text
sql/ 是唯一 SQL 源目录；
db/init/ 只是 Docker 执行入口；
数据库命名全部小写 snake_case；
Mock 字段全部来自 docs/api/mock-contract.md；
系统演示导入与正式初始化导入分开；
D 负责总控，但 A/B/C 必须交付各自材料。
```

按这个方案执行，四个人可以相对独立推进，A 不会成为阻塞点，D 也不会独自承担所有后期压力，最终更容易形成一个完整、可演示、可分析、报告证据充分的高分课程设计项目。
