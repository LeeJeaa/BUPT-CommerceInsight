# 成员 A 开发规划

> 适用分支：`dev/a-database-sql`  
> 适用角色：成员 A，数据库核心与 SQL 资产负责人  
> 依据文档：`README.md`、`docs/00_冻结文档.md`、`docs/分工指南.md`、`docs/database/*` 规范文档  
> 核心原则：`sql/` 是唯一 SQL 源资产目录；数据库对象统一小写 `snake_case`；禁止双引号对象名。
> 规划方式：按开发周期和可独立交付物划分，尽量让 A 不等待 B/C/D 即可推进。

---

## 1. 成员 A 工作边界

### 1.0 独立开发原则

成员 A 的开发应按“数据库资产可以独立构建、独立验证、独立交付”的方式推进。

执行原则：

1. A 先完成 `sql/` 源资产，不等待后端接口。
2. A 使用本地 PostgreSQL 或最小样例数据验证 SQL，不等待 D 的正式 Docker 和 COPY。
3. A 输出稳定字段语义和 SQL 契约，B 只按契约接入。
4. A 不等待 C 页面；C 只依赖 B 的 API 字段。
5. A 和 D 的交互集中在 COPY 兼容、索引候选、EXPLAIN 解读，不让 D 反向修改 SQL 逻辑。
6. 每个周期都要形成可提交成果，避免堆到最后一次性联调。

开发节奏采用：

```text
周期 0：基线同步与独立环境
周期 1：表结构骨架
周期 2：约束与样例数据
周期 3：TPC-H 查询资产
周期 4：TPC-C 事务资产
周期 5：导入清洗、触发器、存储过程
周期 6：索引、EXPLAIN、文档证据链
周期 7：对接冻结与验收修正
```

## 4. 表结构设计注意点

### 4.1 TPC-H 表

1. 表名全部小写。
2. 字段名全部小写。
3. 保留 TPC-H 原始字段前缀。
4. 不使用双引号。
5. 数据类型使用 PostgreSQL 合理类型：
   - 主键、外键使用 `integer` 或 `bigint`。
   - 金额使用 `numeric`。
   - 日期使用 `date`。
   - 固定短文本可使用 `char` 或 `varchar`。
6. `lineitem` 和 `orders` 是大表，索引和外键在正式导入后创建。
7. 字段顺序要方便 D 使用 COPY。

### 4.2 TPC-C 表

1. 使用 `tpcc_customer`、`tpcc_orders` 避免与 TPC-H 冲突。
2. `warehouse` 要支持 Payment 更新累计收款。
3. `district` 要支持 Payment 更新累计收款，也要支持 New-Order 获取并递增下一订单号。
4. `tpcc_customer` 要支持余额、支付次数、累计支付金额。
5. `stock` 要支持按仓库和商品扣减库存。
6. `order_line` 要记录订单明细和金额。
7. `history` 要记录 Payment 历史。
8. `transaction_log` 记录事务提交、回滚、耗时和错误信息。

## 5. stock_change_log 设计

### 5.1 表设计建议

```sql
CREATE TABLE stock_change_log (
    log_id bigserial PRIMARY KEY,
    warehouse_id integer NOT NULL,
    item_id integer NOT NULL,
    old_quantity integer NOT NULL,
    new_quantity integer NOT NULL,
    change_quantity integer NOT NULL,
    change_type varchar(50) NOT NULL,
    related_transaction_id varchar(64),
    created_at timestamp NOT NULL DEFAULT current_timestamp
);
```

### 5.2 字段语义

| 字段 | 含义 |
|---|---|
| `log_id` | 日志主键 |
| `warehouse_id` | 仓库编号 |
| `item_id` | 商品编号 |
| `old_quantity` | 变更前库存 |
| `new_quantity` | 变更后库存 |
| `change_quantity` | 变化量，等于 `new_quantity - old_quantity` |
| `change_type` | 变更类型，例如 `new_order` |
| `related_transaction_id` | 关联事务编号 |
| `created_at` | 创建时间 |

### 5.3 实现要求

1. New-Order 扣减库存时必须产生库存日志。
2. 优先通过 `trg_stock_quantity_change` 自动记录。
3. 如果触发器无法可靠获得事务编号，可由 B 在事务 SQL 中显式传递或补写关联编号。
4. C 展示库存变动日志时只能使用 API 字段：
   - `logId`
   - `warehouseId`
   - `itemId`
   - `oldQuantity`
   - `newQuantity`
   - `changeQuantity`
   - `changeType`
   - `relatedTransactionId`
   - `createdAt`

## 7. TPC-C 事务 SQL 流程

### 7.1 New-Order

涉及表：

```text
warehouse
district
tpcc_customer
tpcc_orders
new_order
order_line
item
stock
stock_change_log
transaction_log
```

执行步骤：

1. 开启事务。
2. 生成 `transaction_id`。
3. 校验 `warehouse` 是否存在。
4. 校验 `district` 是否存在。
5. 校验 `tpcc_customer` 是否存在。
6. 读取 `district` 当前下一订单号。
7. 更新 `district` 下一订单号加 1。
8. 插入 `tpcc_orders`。
9. 插入 `new_order`。
10. 循环处理订单明细：
    - 校验 `item`。
    - 校验 `stock`。
    - 读取商品价格和库存。
    - 扣减库存。
    - 插入 `order_line`。
    - 通过触发器或显式 SQL 写入 `stock_change_log`。
11. 计算订单总金额。
12. 写入 `transaction_log`，状态为 `committed`。
13. 提交事务。
14. 任一步失败则回滚，并记录失败原因。

返回字段由 B 组装：

```text
transactionId
status
orderId
totalAmount
elapsedMs
```

### 7.2 Payment

涉及表：

```text
warehouse
district
tpcc_customer
history
transaction_log
```

执行步骤：

1. 开启事务。
2. 生成 `transaction_id`。
3. 校验 `warehouse` 是否存在。
4. 校验 `district` 是否存在。
5. 校验 `tpcc_customer` 是否存在。
6. 更新 `warehouse` 累计收款金额。
7. 更新 `district` 累计收款金额。
8. 更新 `tpcc_customer` 余额、支付次数、累计支付额。
9. 插入 `history`。
10. 写入 `transaction_log`，状态为 `committed`。
11. 提交事务。
12. 任一步失败则回滚，并记录失败原因。

返回字段由 B 组装：

```text
transactionId
status
customerId
newBalance
elapsedMs
```
