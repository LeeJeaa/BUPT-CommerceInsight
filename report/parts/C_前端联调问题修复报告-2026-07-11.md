## 1. 修复背景

本轮修复来自真实后端联调验收反馈，原始要求为：

```text

负责范围：frontend/，不修改数据库字段和后端 SQL。

修复导入表选项不一致：
- 移除 partsupp 选项，保留 orders、lineitem。

- 导入成功后直接展示后端返回的最终状态、成功/失败行数与耗时。

- 当真实 API 没有性能结果时，显示空状态和“暂无结果，请先运行压测”。
- 后端写入性能数据后，/performance 页面可展示 tpch 与 tpcc 两类结果。

- 保留 Mock 模式，但 Mock 字段必须与新的性能入库 DTO/查询响应一致。

完成真实 API 联调回归：
- 管理员登录、注册、审批、禁用；

- 后端 403 时显示无权限，而不是只依赖路由隐藏按钮。
```

本轮目标是让前端在 Mock 模式和真实 API 模式下都能稳定验收，并在真实后端空数据、无压测结果、无权限、登录失效等场景下给出清晰页面状态。

## 3. 真实联调发现的问题

真实后端启动后，前端以如下方式切换真实 API 模式：

```powershell
cd frontend
$env:VITE_USE_MOCK="false"
npm.cmd run dev
```

联调过程中发现：

- 未导入正式 TPC-H 数据时，业务查询、业务分析为空是正常现象。
- `dashboard/summary` 显示 TPC-H 核心表行数均为 0，说明当前真实库尚未执行 D 负责的 `dbgen + COPY` 正式导入。
- Q1/Q5/Q12 在空库下可正常返回 `200` 和 `rowCount=0`。
- Q14 在空库下返回 `500`，表现为前端 TPC-H Q14 页面显示“服务端错误”。

经接口复现：

```text
GET /api/tpch/q1  -> 200, rowCount=0
GET /api/tpch/q5  -> 200, rowCount=0
GET /api/tpch/q12 -> 200, rowCount=0
GET /api/tpch/q14 -> 500
```

进一步诊断后确认，Q14 问题不是前端渲染问题，而是后端在处理空聚合结果时缺少兜底。

## 4. 后端 Q14 小调整说明

虽然成员 C 的主要负责范围是 `frontend/`，但为保证真实联调验收闭环，本轮顺手修复了一个很小的后端空结果兜底问题。该修复不修改数据库字段、不修改表结构、不改变接口路径和响应字段。

修改文件：

- `backend/src/main/resources/mapper/tpch/TpchMapper.xml`
- `backend/src/main/java/com/bupt/commerceinsight/tpch/MyBatisTpchService.java`
- `backend/src/test/java/com/bupt/commerceinsight/tpch/MyBatisTpchServiceTest.java`

问题原因：

Q14 是聚合查询。真实库没有 `lineitem` 数据时，SQL 会返回一行聚合结果，但 `promo_revenue_percent` 为 `NULL`。MyBatis 在该场景下可能把这一行映射为 `null` 对象。原后端代码直接调用：

```java
records.get(0).getPromoRevenuePercent()
```

因此在空库下触发 `NullPointerException`，最终接口返回 500。

修复方式：

- SQL 层对 Q14 结果增加 `COALESCE(..., 0)`，空数据时返回 0。
- Java 层增加 `records.get(0) == null` 和字段为 `null` 的双重防御。
- 当 Q14 空聚合时，后端规范化返回一条 `promoRevenuePercent = 0` 的记录。
- 新增单元测试覆盖 MyBatis 返回 `[null]` 的场景。

修复后行为：

```text
GET /api/tpch/q14?month=2020-09-01
```

空库下由原来的 `500` 修复为：

```text
200 success
rowCount=1
promoRevenuePercent=0
```
